# cobblestone documentation

The API reference is on [docs.rs](https://docs.rs/cobblestone). This guide
covers how to use the crate, the guarantees it gives, and how it is built and
tested.

## Overview

Cobblestone-128 uses AES-128-GCM and HKDF-SHA-512. It encrypts messages of up to
4 PiB, and supports authenticated streaming encryption and decryption as well as
authenticated random access. The message is split into 16 KiB chunks. Each chunk
is encrypted and authenticated separately, and the scheme protects against
reordering and truncation. The fixed overhead is 56 bytes, and the marginal
overhead is about 0.1%.

It is interoperable with the Go ([filippo.io/cobblestone](https://github.com/FiloSottile/cobblestone)),
Python ([pyca/cryptography](https://cryptography.io/en/latest/cobblestone/)) and
TypeScript ([cobblestone.ts](https://github.com/FiloSottile/cobblestone.ts))
implementations, and passes the Wycheproof test vectors.

### Cobblestone-256

Cobblestone-256 is the same scheme with AES-256-GCM and 32-byte keys. The spec
describes it as compliance-oriented and recommends Cobblestone-128 absent other
requirements, so it is behind a feature, for environments that require 256-bit
keys:

```sh
cargo add cobblestone --features cobblestone-256
```

Use a `Key256` instead of a `Key`: every API accepts either, and the key type
selects the instantiation. The header doesn't record which one was used, so a
message must be decrypted with the same type of key. pyca/cryptography also
implements Cobblestone-256.

## Usage

In memory:

```rust
use cobblestone::{Key, decrypt, encrypt};

fn main() -> Result<(), cobblestone::Error> {
    let key = Key::generate();
    let ciphertext = encrypt(&key, b"file.txt", b"hello world")?;
    let plaintext = decrypt(&key, b"file.txt", &ciphertext)?;
    assert_eq!(plaintext, b"hello world");
    Ok(())
}
```

Streaming, with constant memory use whatever the size of the message:

```rust
use std::io::{self, Read, Write};

use cobblestone::{DecryptReader, EncryptWriter, Key};

fn main() -> io::Result<()> {
    let key = Key::generate();

    let mut w = EncryptWriter::new(&key, b"backup", Vec::new());
    w.write_all(b"hello ")?;
    w.write_all(b"world")?;
    let ciphertext = w.finish()?; // Required: writes the final chunk.

    let mut r = DecryptReader::new(&key, b"backup", &ciphertext[..]);
    let mut plaintext = Vec::new();
    r.read_to_end(&mut plaintext)?;
    assert_eq!(plaintext, b"hello world");
    Ok(())
}
```

Random access, reading only the chunks that cover the requested range:

```rust
use std::io::{self, Cursor};

use cobblestone::{Key, RandomAccessDecryptor};

fn main() -> io::Result<()> {
    let key = Key::generate();
    let message: Vec<u8> = (0..100_000u32).map(|i| i as u8).collect();
    let ciphertext = cobblestone::encrypt(&key, b"", &message).unwrap();

    // Usually a File. The message length is authenticated on creation.
    let mut r = RandomAccessDecryptor::new(&key, b"", Cursor::new(ciphertext))?;

    // Read 10 bytes at offset 50,000.
    let mut buf = [0; 10];
    r.read_exact_at(&mut buf, 50_000)?;
    assert_eq!(buf, message[50_000..50_010]);
    Ok(())
}
```

`RandomAccessDecryptor` also implements `Read + Seek`, for code that expects a
seekable reader.

Async, with the `tokio` feature. The async types have the same names as the
blocking ones, under `cobblestone::tokio`:

```rust
use cobblestone::Key;
use cobblestone::tokio::{DecryptReader, EncryptWriter};
use tokio::io::{AsyncReadExt, AsyncWriteExt};

#[tokio::main(flavor = "current_thread")]
async fn main() -> std::io::Result<()> {
    let key = Key::generate();

    let mut w = EncryptWriter::new(&key, b"upload", Vec::new());
    w.write_all(b"hello world").await?;
    w.shutdown().await?; // Required: writes the final chunk and shuts down the inner writer.
    let ciphertext = w.into_inner();

    let mut r = DecryptReader::new(&key, b"upload", &ciphertext[..]);
    let mut plaintext = Vec::new();
    r.read_to_end(&mut plaintext).await?;
    assert_eq!(plaintext, b"hello world");
    Ok(())
}
```

### Sending more data after a ciphertext

The ciphertext has no length field, and a decryptor reads its input to the
end. If you send anything after a ciphertext on the same stream, tell the
receiver where the ciphertext ends, for example by sending its
`ciphertext_size` first.

## Keys

The spec requires the key to be "uniformly random, e.g. generated by a CSPRNG
or output by a KDF". `Key::generate` uses the operating system's CSPRNG. For a
key from elsewhere, such as KDF output or a key you stored earlier, use
`Key::from_bytes`. Neither the library nor the other implementations can check
that a key is random, so never pass a password or other guessable secret
directly; run it through a password KDF such as Argon2 first. A single key can
encrypt a practically unlimited number of messages, because each message gets a
fresh random salt.

`Key` validates its length when it's created, so no other API can fail because
of the key. It is zeroized when dropped, compares in constant time, and is
redacted from its `Debug` output.

## Context

The context is a non-secret byte string bound to the ciphertext, such as a
filename, a user ID, or a purpose like `b"myapp v2 backups"`. Decryption only
succeeds with the same context. It is not encrypted and not stored in the
ciphertext. Pass `b""` when there is nothing to bind; the spec treats an empty
context and no context the same. Strings can be passed with `.as_bytes()`.

## Errors

The one-shot functions return `cobblestone::Error`. The streaming types return
`io::Error`; when the cause is the ciphertext, it wraps a `cobblestone::Error`,
which `io::Error::downcast` recovers:

```rust
use std::io::Read;


fn main() {
    let key = cobblestone::Key::generate();
    let ciphertext = cobblestone::encrypt(&key, b"", b"hello world").unwrap();
    let truncated = &ciphertext[..ciphertext.len() - 1];

    let mut r = cobblestone::DecryptReader::new(&key, b"", truncated);
    let err = r.read_to_end(&mut Vec::new()).unwrap_err();
    match err.downcast::<cobblestone::Error>() {
        Ok(cobblestone::Error::DecryptionFailed { chunk }) => {
            println!("chunk {chunk} failed to authenticate");
        }
        Ok(other) => println!("invalid ciphertext: {other}"),
        Err(io_err) => println!("I/O error: {io_err}"),
    }
}
```

Decryption never returns unauthenticated plaintext. A streaming decryptor can
return a valid prefix of an invalid message before it fails, and once it fails,
every later read fails too. The end of the message is only reported after the
final short chunk has been authenticated, so truncation is always detected.

Keys and salts come from the operating system's random number generator, via
`getrandom`. If it fails, the library panics instead of returning an error,
like the Go and TypeScript implementations. That doesn't happen on supported
platforms, and it means encryption can only fail for oversized messages and
I/O errors.

## Blocking or async?

The crypto costs the same either way: about 6 µs per 16 KiB chunk on an Apple
M5 (roughly 3 GB/s). The async types don't make the crypto non-blocking. What
they avoid is holding a thread while *waiting* for data.

Splitting the message into chunks doesn't, on its own, give the thread back to
the runtime. A tokio task only yields when a future returns `Pending`, and the
async decryptor only does that when its source has no data ready. While data is
available it keeps decrypting, chunk after chunk, in one go.

Measured on a single-threaded runtime (Apple M5, 32 MiB message), as the longest
time another task was kept waiting:

| Source | Total time | Longest wait for other tasks |
|---|---|---|
| One-shot `decrypt`, in memory | 13 ms | 13 ms (the whole run) |
| `tokio::DecryptReader` over a `&[u8]` | 15 ms | 15 ms (the whole run) |
| `tokio::DecryptReader` over TCP, sender at about 100 Mbit/s (4 MiB) | 384 ms | 0.7 ms |
| `tokio::DecryptReader` over local TCP, sender at full speed | 22 ms | 3 ms |

- **Local files, CLI tools, batch jobs:** use the blocking types.
- **In a tokio service, streaming to or from the network:** use the async
  types. When the peer is slower than the crypto, which is the usual case, the
  task parks between packets and only holds the thread briefly. A blocking
  reader would hold a thread for the whole transfer.
- **Data arriving faster than it can be decrypted:** the socket rarely runs
  dry, so the task yields only when tokio's cooperative budget forces it, which
  can take milliseconds. If that latency matters to other tasks, decrypt on a
  dedicated thread pool instead.
- **Data already in memory:** neither `encrypt`/`decrypt` nor the async types
  yield, because the source is always ready. Use
  `tokio::task::spawn_blocking` for anything large.
- **`tokio::fs::File` as the source:** wrap it in a large
  `tokio::io::BufReader` (for example 1 MiB). Every `tokio::fs` read goes
  through tokio's blocking thread pool, and without a buffer decryption took
  about 60% longer in a benchmark on a 3 MiB file.

## Implementation notes

- The crypto comes from RustCrypto (`aes-gcm`, `hmac`, `sha2`). HKDF-Expand is
  written by hand on top of `hmac`, because the `hkdf` crate rejects PRKs
  shorter than the hash output, and Cobblestone uses the input key directly as
  the PRK.
- The blocking and async types share one I/O-free state machine
  (`src/stream.rs`), so truncation, chunk counting and sticky errors are
  implemented once.
- Raw mode (caller-supplied AEAD key and base nonce) is implemented internally
  in `src/raw.rs` but not exposed. The spec says libraries SHOULD NOT expose it
  to applications. It is tested against the raw-mode vectors for both
  AES-128-GCM and AES-256-GCM.

## Testing

```sh
cargo test --all-features
```

This runs:

- **Wycheproof vectors** (`tests/testdata`, vendored unmodified from
  [C2SP/wycheproof](https://github.com/C2SP/wycheproof); see
  `tests/testdata/README.md` for the upstream commit). Each vector goes
  through every API: one-shot, streaming with whole input, 1000-byte reads and
  1-byte reads, random access, tokio, and re-encryption. The tests check prefix and sticky-error behavior on invalid
  vectors, as the cobblestone.ts suite does. Raw mode is tested for both
  instantiations. The Cobblestone-256 vectors only go through the public APIs
  with the `cobblestone-256` feature, which `--all-features` enables.
- **Doctests**, including the Rust examples in this file and the README. They run with
  `--all-features`, since one of them needs `tokio`.
